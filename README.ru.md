# URL Checker

[English](README.md) · **Русский**

Небольшой сервис, который асинхронно проверяет список URL и показывает результат по мере готовности. Вы вставляете список адресов, бэкенд отправляет на каждый HEAD-запрос, а интерфейс опрашивает статус, пока у каждого URL не появится итог. Проверки идут по пять одновременно, задачу можно отменить на ходу.

Стек из задания: Node.js + TypeScript + NestJS на бэкенде, React + TypeScript + Zustand на фронтенде. Данные хранятся в памяти, без базы.

## Запуск

### Docker (оба сервиса сразу)

```bash
docker compose up --build
```

- Интерфейс: http://localhost:8080
- API: http://localhost:3000

nginx отдаёт собранный фронтенд и проксирует `/api` на бэкенд, поэтому браузер работает с одним источником.

### Готовые образы (без локальной сборки)

CI публикует оба образа в GitHub Container Registry при каждом пуше в `main`. Чтобы запустить их без сборки:

```bash
docker compose -f docker-compose.ghcr.yml up
```

Адреса те же. Образы: `ghcr.io/ismoiljon1101/async-url-checker-backend` и `-frontend`.

Откройте http://localhost:5173.

### Тесты

```bash

```

34 теста покрывают то, что легко сломать: метод HEAD, ограничение одновременности (в том числе попытку поднять его через переменную окружения), искусственную задержку, отмену, обработку HTTP-кодов, нормализацию адреса, все пять статусов задачи и разделение `error` / `cancelled` у URL, согласованность таймингов у URL, стабильность ETag после отмены, ограничение памяти хранилища и сопоставление ETag. Они гоняют сервисы напрямую с подменённым `fetch`, поэтому весь набор проходит за пару секунд.

## API

Базовый путь `/api/jobs`. Все ответы используют один набор статусов из `libs/enums`.

| Метод | Путь | Что делает |
| --- | --- | --- |
| `POST` | `/api/jobs` | Создать задачу. Тело: `{ "urls": ["https://..."] }`. Возвращает `{ "jobId": "..." }` со статусом `pending`, рядом идёт сводка, чтобы клиенту не делать второй запрос. |
| `GET` | `/api/jobs` | Список задач, свежие сверху: `id`, `createdAt`, `status` и сводная статистика. |
| `GET` | `/api/jobs/:id` | Одна задача с разбивкой по URL. |
| `DELETE` | `/api/jobs/:id` | Отменить задачу. Останавливает и очередь, и запросы в полёте. |
| `GET` | `/health` | Проверка живости, её использует healthcheck в compose. |

Статус задачи — одно из `pending`, `in_progress`, `completed`, `cancelled`, `failed`. У каждого URL свой статус: `pending`, `in_progress`, `success`, `error`, `cancelled`.

Отменённый URL получает `cancelled`, а не `error`. Его не проверили и он упал, его вообще не проверяли. Если свалить эти два состояния в одно, отменённая задача на 1000 URL отчитается о тысяче ошибок.

У каждого результата четыре поля времени:

| Поле | Что значит |
| --- | --- |
| `startedAt` | когда URL пошёл в обработку |
| `finishedAt` | когда дошёл до конечного статуса |
| `durationMs` | `finishedAt - startedAt`, то есть вместе с искусственной задержкой |
| `requestMs` | сам HEAD-запрос, без задержки |

Разделены намеренно. `durationMs` — это в основном задержка, поэтому про сам URL говорит `requestMs`, и именно его показывает интерфейс.

Быстрая проверка через curl:

```bash
curl -X POST http://localhost:3000/api/jobs \
  -H "Content-Type: application/json" \
  -d '{"urls":["https://example.com","https://github.com"]}'
```

## Как устроено

### Схема сначала

Типы начинаются с перечислений. `job-status.enum.ts` и `url-status.enum.ts` задают допустимые состояния, модели типов строятся на них, а DTO проверяет единственное, что приходит извне. Ниже по коду никто не выдумывает свою строку для «completed». Фронтенд повторяет те же перечисления, поэтому оба приложения говорят на одном языке по сети.

### Структура

Бэкенд следует модульной системе NestJS: функциональные модули в `components/`, общий код в `libs/`, тонкий корневой модуль.

```
backend/src/
  app.module.ts          корневой модуль, импортирует модули
  main.ts                bootstrap (CORS, ValidationPipe, фильтр ошибок)
  components/
    jobs/                модуль задач
      jobs.controller.ts   только маршруты
      jobs.service.ts      оркестрация жизненного цикла
      jobs.repository.ts   хранилище в памяти (граница персистентности)
      url-checker.service.ts  HEAD-проверки, пул на 5, отмена
      jobs.module.ts       связывает всё через DI
  libs/                  общее для всех модулей
    dto/ enums/ types/   схема запроса, словарь статусов, доменные типы
    utils/               пул одновременности, нормализатор URL
    filters/             глобальный фильтр исключений

frontend/src/
  features/jobs/         api, store, компоненты, типы модуля задач
  shared/                http-клиент, UI (StatusBadge, переключатель языка), i18n
  app/  styles/
```

`JobsService` владеет переходами состояний, `JobsRepository` — хранением, `UrlCheckerService` — самой проверкой. Такое разделение позволяет тестировать логику одновременности и отмены отдельно, без HTTP.

### Двуязычный интерфейс

Интерфейс есть на английском и русском. Переключатель в шапке запоминает выбор, а при первом заходе приложение берёт язык браузера. Строки лежат в одном словаре (`shared/i18n`), с ключами и типами: пропущенный перевод — это ошибка компиляции.

### Одновременность и отмена

Проверяющий гоняет общий курсор по массиву URL: пять воркеров берут следующий индекс, пока массив не опустеет. Так число одновременных запросов держится на пяти без сторонней очереди. Перед запросом каждый URL ждёт случайные 0–10 секунд, как в задании.

У каждой задачи один `AbortController`. Отмена прерывает его — это разом снимает искусственную задержку и любой запрос в полёте, а оставшиеся URL переводятся в финальное состояние, чтобы числа сходились. Слишком долгий запрос обрывается своим 15-секундным таймаутом.

`POST` намеренно возвращает `pending`. Запуск отложен на следующий тик, поэтому клиент получает id задачи до старта проверок и дальше следит за прогрессом.

### Опрос и его удешевление через ETag

Store держит два интервала вне React, чтобы они переживали перерисовки. Список обновляется раз в две секунды. Открытая задача — раз в секунду и останавливается, как только доходит до финального статуса. Смена задачи сразу сбрасывает старую деталь и игнорирует запоздалый ответ по той, что вы только что покинули, так что медленный ответ не перекроет текущий вид.

Каждый GET несёт `ETag` на основе версии (счётчик у задачи и глобальный для списка). Клиент шлёт `If-None-Match`; если ничего не изменилось, сервер отвечает `304` с пустым телом и вообще не сериализует ответ. Завершённая задача, которую UI продолжает опрашивать, стоит несколько байт заголовков вместо полного тела. Сравнение версий O(1), что быстрее ETag по хешу тела.

### Ограниченная память

Хранилище — это `Map` как упорядоченная структура. «Свежие сверху» — это reverse, а не сортировка. Число хранимых задач ограничено (`MAX_JOBS`, по умолчанию 500); при превышении вытесняется самая старая *завершённая* задача, поэтому процесс не растёт без предела, а активную задачу не выкинут на ходу. Счётчики по URL обновляются на каждом переходе, поэтому сводка O(1), а не пересчёт O(n).

### Почему не несколько ядер

Проверка I/O-bound — она ждёт сокеты, поэтому один event loop уже ведёт много запросов сразу, и лишние ядра или потоки ничего не дают. Ограничение одновременности (5) и искусственная задержка — это требования ТЗ, и именно они определяют общее время большой пачки, а не CPU. Хранение в памяти также исключает кластеризацию: отдельные процессы держали бы отдельные map. И `MAX_CONCURRENCY`, и `MAX_CHECK_DELAY_MS` настраиваются через env для локальных нагрузочных прогонов; по умолчанию — 5 и 0–10с из ТЗ.

## Заметки

- Хранение в памяти — по заданию. Задачи сбрасываются при перезапуске бэкенда. Переход на Redis или Postgres — это замена хранилища за `JobsRepository`, выше по коду ничего не меняется.
- HEAD — правильный выбор для проверки живости: он не тянет тело. Некоторые хосты отвечают на HEAD странно или отказывают. Тогда URL возвращается как `error` с сообщением, что для чекера честный результат.
- Искусственная задержка настраивается через `MAX_CHECK_DELAY_MS`, поэтому тесты идут мгновенно, а ограничение одновременности видно без ожидания.
- Голый хост вида `google.com` нормализуется в `https://google.com` перед проверкой, так как `fetch` требует абсолютный URL.
